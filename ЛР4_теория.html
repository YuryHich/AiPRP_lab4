Есть два способа поговорить с сервером. Первый — обычный адрес в браузере: спросил время или пример, получил одну записку и связь закрылась. Второй — чат: соединение остаётся открытым, можно писать много сообщений подряд. Время и калькулятор умеют оба способа.

REST и Jersey

Веб-сервис в этой лабе — REST. Клиент делает обычный HTTP GET, сервер отвечает текстом JSON. Не SOAP и не WSDL: связь идёт по URL и методу.

Класс с аннотациями сам по себе порт не слушает. Его публикует библиотека Jersey. В web.xml зарегистрирован сервлет org.glassfish.jersey.servlet.ServletContainer. Он смотрит пакет com.example.service, находит классы с @Path и вешает их на /api/*.

АннотацияЗачем
@Path("/time")кусок адреса после /api
@GETметод срабатывает на GET, не на POST
@Produces(APPLICATION_JSON)ответ — JSON, заголовок Content-Type
@QueryParam("expr")значение из ?expr=2+4*7

Полный адрес складывается так: хост и порт Tomcat, имя WAR, шаблон сервлета, путь ресурса.

http://localhost:8079/TimeService/api/time
http://localhost:8079/TimeService/api/calc?expr=2+4*7
+ Объяснить проще

Jersey — диспетчер. Браузер стучится в /api/что-то. Диспетчер смотрит табличку аннотаций и зовёт нужный метод. @Path — имя кабинета, @GET — «это вопрос, не приказ записать», @Produces — «ответ будет в формате JSON».

Разбор: TimeResource

TimeService/src/main/java/com/example/service/TimeResource.java

@Path("/time")
public class TimeResource {
    @GET
    @Produces(MediaType.APPLICATION_JSON)
    public String getCurrentTime() {
        DateTimeFormatter formatter = DateTimeFormatter.ofPattern("HH:mm:ss");
        String currentTime = LocalTime.now().format(formatter);
        return "{\"time\": \"" + currentTime + "\"}";
    }
}

Это код из методички без изменений по смыслу. LocalTime.now() берёт время компьютера, формат HH:mm:ss. Строка собирается руками, отдельная библиотека JSON не нужна. Проверенный ответ выглядел как {"time": "19:25:12"}.

Разбор: калькулятор

Calculator.java и CalcResource.java

CalcResource — тот же набор аннотаций, путь /calc. Параметр expr уходит в Calculator.json.

Calculator.evaluate разбирает строку слева направо: число, знак, число, знак... Числа бывают целые и дробные, перед числом можно поставить минус, пробелы не важны. Скобок по заданию нет, поэтому хватает двух проходов:

  1. сначала выполняются * и /: 2+4*7 превращается в 2+28;
  2. потом + и - слева направо: 2+28 = 30.

Считается в BigDecimal, чтобы 0.1+0.2 давало 0.3, а не 0.30000000000000004. Целый результат выводится без хвоста: 30, а не 30.0. Ошибки — деление на ноль, лишний символ, выражение обрывается на знаке — приходят полем error.

{"expression": "2+4*7", "result": 30}
{"expression": "10-6/3", "result": 8}
{"expression": "7/2", "result": 3.5}
{"expression": "1/0", "error": "деление на ноль"}

Тонкость адреса: в строке запроса + по правилам URL означает пробел, и ?expr=2+4*7 пришло бы как 2 4*7. Поэтому параметр берётся с @Encoded (как есть, без расшифровки), + сохраняется, а остальное расшифровывается вручную. Так пример из задания работает прямо из адресной строки браузера.

+ Объяснить проще

Как в школе: сначала умножаем и делим, потом складываем и вычитаем. Калькулятор проходит по примеру два раза — первый раз собирает все умножения, второй раз складывает то, что осталось. REST и чат зовут один и тот же калькулятор, поэтому ответы у них не разъедутся.

web.xml

src/main/webapp/WEB-INF/web.xml

<servlet-class>org.glassfish.jersey.servlet.ServletContainer</servlet-class>
<param-name>jersey.config.server.provider.packages</param-name>
<param-value>com.example.service</param-value>
<url-pattern>/api/*</url-pattern>

Схема Java EE 3.1, как в методичке, потому что Tomcat 9 понимает javax, не jakarta. load-on-startup 1 — Jersey поднимается вместе с приложением, не при первом запросе.

WAR называется TimeService.war. Tomcat кладёт его в webapps и публикует как /TimeService.

Зависимости в pom.xml: javax.ws.rs-api 2.1.1 (тот jar, который методичка качает отдельно), Jersey 2.41 (jersey-container-servlet и jersey-hk2), API веб-сокета provided — его даёт сам Tomcat.

Веб-сокет

websocket/chat/ChatAnnotation.java и webapp/websocket/chat.xhtml

Обычный HTTP: запрос — ответ — соединение закрыто. Веб-сокет: сначала HTTP-рукопожатие, потом канал остаётся открытым. Сообщения ходят в обе стороны без нового запроса на каждое слово.

Сервер:

@ServerEndpoint(value = "/websocket/chat")
public class ChatAnnotation
  • @OnOpen — гость подключился, всем пишем «has joined»;
  • @OnMessage incoming — пришло сообщение;
  • @OnClose — «has disconnected»;
  • broadcast — текст уходит всем открытым сессиям.

Что делает incoming, вариант 1 плюс пример времени из второй части методички:

  • time → Current time: HH:mm:ss;
  • выражение из цифр и знаков → Результат: 2+4*7 = 30, при ошибке Ошибка: деление на ноль;
  • любой другой текст → Guest0: текст.

Клиент — страница chat.xhtml. В JavaScript:

Chat.connect('ws://' + window.location.host + '/TimeService/websocket/chat');
Chat.socket.send(message);

Enter в поле отправляет строку. onmessage дописывает ответ в голубой блок. Адрес сокета — ws://, не http://. Страница: http://localhost:8079/TimeService/websocket/chat.xhtml.

Проверка клиентом JDK: после «2+4*7» сервер прислал Результат: 2+4*7 = 30. После «time» — строку с часами.

Контрольные вопросы

1. Что такое управляемый web-сервис, как он связывается с клиентом?

Управляемый сервис — класс, который контейнер сам создаёт и публикует. Мы не пишем main и не слушаем порт. Tomcat поднимает Jersey-сервлет, Jersey по аннотациям находит TimeResource и CalcResource.

Связь с клиентом — HTTP. Клиент открывает URL. Метод GET попадает в метод с @GET. Параметры приходят из строки запроса (expr). Ответ — тело HTTP, у нас JSON, тип задаёт @Produces. После ответа это соединение для данного запроса заканчивается.

2. Как создать web-сервис?

  1. Проект Java Web / Maven WAR.
  2. Пакет com.example.service, класс с @Path, @GET, @Produces.
  3. Библиотека Jersey и javax.ws.rs-api.
  4. web.xml: сервлет ServletContainer, параметр jersey.config.server.provider.packages, адрес /api/*.
  5. Собрать WAR, положить в webapps Tomcat 9, открыть http://localhost:8079/TimeService/api/time.

3. Что такое веб-сокет?

Протокол поверх TCP для постоянной двусторонней связи. Браузер открывает его объектом WebSocket. Сервер помечает класс @ServerEndpoint. После рукопожатия обе стороны шлют текстовые кадры, не оформляя каждый как новый HTTP-запрос. В лабе это чат: вход, реплики, время и результаты вычислений рассылаются всем подключённым.

4. Как создать веб-сокетное соединение?

Сервер: класс ChatAnnotation, @ServerEndpoint("/websocket/chat"), методы @OnOpen, @OnMessage, @OnClose. Класс лежит в WAR, Tomcat сам его публикует.

Клиент: страница chat.xhtml, в скрипте new WebSocket("ws://хост/TimeService/websocket/chat"). По Enter вызывается socket.send. Входящие кадры читает onmessage.

5. Чем веб-сокет отличается от HTTP-запроса?

HTTP-запрос короткоживущий: клиент спросил /api/time, получил JSON, канал закрыт. Сервер сам не пишет клиенту, пока тот снова не спросит. Веб-сокет после открытия живёт долго, сервер может прислать сообщение первым (у нас «Guest has joined»), и одно сообщение видят все участники чата. Адрес другой: ws:// вместо http://. Общее только то, что сокет начинается с HTTP-рукопожатия Upgrade.
